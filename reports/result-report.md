## 三、本轮修复的缺陷（按发现顺序）

### 3.1 决策带宽不足 —— 新行动挤占既有行为（第 9 次复发）

**现象**：接入 `found`（创办企业）后存活率崩塌（seed1 15/50、seed2 0/50），基线是 50/50。

**定位**：直接读候选窗口的探针给出
`window=[craft,build,expedition,write,found,drink]` —— `eat` 与 `forage` **根本不在窗口里**。
候选窗口由 `selector.shortlist` 与 `pruner.prune` 两级**纯分数截断**产生，
而生存骨架的基础分最低（forage/rest 0.2、eat/drink 0.3），新增行动后必然被挤出。

**修复（三级，缺一不可）**：

1. 两级闸门**同时**豁免生存骨架 —— 只修 `pruner` 后窗口仍是
   `[drink,craft,build,expedition,write,found]`，`eat`/`forage` 依旧缺席；
2. 发展行动（found/socialize/court/accept）各占独立席位 ——
   `socialize` 是社交边的唯一来源，`court`/`accept` 是生育的唯一入口且有时间窗口；
3. `shortlist.limit` 与 `pruneK` 对齐到 12 —— `shortlist(12)` + `prune(6)` 时
   `build` 仍会被 `craft` 挤掉（60 tick 小局 `built=0`）。

**代价与教训**：这一轮在 `limit` 上试了 6/8/10/12 四个值才想到去打印实际窗口，
浪费数轮。**先看事实再调参**。

### 3.2 识字曾是全局布尔

`literacyRate > 0` 即全体识字 → 「写书」要么人人可做、要么无人可做。
最终拆成供给层（是否有教师在职）+ 个人层（每 tick 按全城人口算出识字**人数**
`ceil(share × N)`，再按 id 哈希排序挑出具体是谁）。

为什么用名次而不是逐个哈希阈值：3 人局里三人全部落在 0.4 阈值之上（概率约 22%），
识字者为零 → 写书行动消失，两个冒烟测试失败。

### 3.3 语义记忆（D1）只记不用

语义记忆被召回后仅写入决策日志，从未进入 `scoreFn` —— 记忆对行为零影响。
现在按标签统计「为当前需求我过去惯用什么行动」，给出**有界且只抬正分**的加成（≤ +25%）。
只抬正分是刻意的：负分代表「此刻不该做」，不该被习惯翻案；25% 上限保证不颠倒量级差异。
**记忆应塑造「怎么做」，不应否决「必须做」** —— 这正是 3.1 的教训。

### 3.4 观察者看不到社交内容与书籍身份

- `social.platform.post` 的 payload 不含 `content` → 编年志里「居民说了什么」整体不可见；
- `agent.action.write.started` 的 `bookId` 恒为 `null` —— bookId 在**完稿时**才生成，
  发起时并不存在。改为记录 `jobId` + 标题/正文，并新增 `agent.action.write.completed`。

### 3.5 发帖正文罐头化

正文从 3~4 条固定模板里随机取，同一处境下逐字相同。
改为 **处境数值 + 人格口吻**合成：数值让「有多严重」可读，口吻让「是谁在说」可辨。

### 3.6 家族系统在运行时完全没接通（三处独立断裂）

用户规格：「连续三代未遗失的特质固定为家族特质，最多 5 个」。实测各家族特质数恒为 0。

1. **每出生一个孩子就新建一个家族**，代际硬编码 → 每个家族永远两代，三代不可达；
2. **生育上限硬编码 2** → 每次运行最多出生 2 人，家族无法长大；
3. **detector / enforcer 没有任何运行时调用点**；`offspring.request` 虽接受
   `familyTraits`，`runProcreation` 却从不传。

三处都已修复（子代并入既有家族、上限可配、生育前结算并遗传特质）。
新增端到端回归锁：真跑主循环断言第三代确实出现、特质确实固化且来自成员真实标签、
且进入后代标签集。

**这是本轮最重要的方法论教训**：单元测试全绿而端到端为 0 ——
`detector`/`enforcer` 的单元测试一直是通过的，但它们从未被主循环调用过。
**只有端到端跑一遍才能发现这类断裂**。

### 3.7 容量天花板把零死亡的小镇判成「余粮不足」

储备容量只在播种期按初始人口算一次（4 × 50 = 200）。人口涨到 74 后人均容量从 4 掉到 2.7，
库存顶在天花板上（人均 1.9~2.0 而非 4），触发 `scoreAction` 里硬编码 2.5 的「自家有粮才谈发展」
闸门 —— `work` 从 24.7% 崩到 **0.8%**、几近灭绝，居民整天休息（`rest` 27.6%）。

两处独立修复：人口变化时按人均容量重算**上限**（只上调容量、不动库存，
避免凭空发粮掩盖真实稀缺）；参照量改用 `config.initialReservePerCapita`。

修复后 `work` 回到 19.1~21.0%，最大单一行动占比降到 20.6%。

### 3.8 图存储全量查询的性能塌陷

CPU 采样显示 **88% 的时间花在 `structuredClone`**。定位到 `graph.read({ type })`：
48 个调用点、返回整批节点的深拷贝，单次成本随节点数线性增长
（300 节点 0.65ms / 3000 节点 7.8ms / 30000 节点 51ms）。长跑后图里积累数万节点
（日志与语义记忆），整个测试套件因此被拖长数分钟。

三处修复：`read({ type })` 改为**惰性只读视图**（首次读 `data`/`edges` 才克隆，对外语义不变）；
语义记忆主循环写入改为 `persist: false`（只留内存索引，这是全系统写入量最大的位置，
50 × 200 = 10000 条）；热路径上把每候选行动一次的市场查询提到每次决策一次。

## 四、哪些设计假设被证伪

这一节比「修好了什么」更重要 —— 它记录了**看起来已经实现、实际从未发生**的能力。

| 假设 | 曾经的证据 | 实际情况 |
|------|-----------|---------|
| 家族三代特质固化已实现 | `detector` / `enforcer` 单元测试全绿 | 运行时**从未调用**，各家族特质数恒为 0 |
| 生育会形成多代家族 | 有子代、有谱系、有家族登记 | 每胎新建家族 + 上限 2 → 结构上不可能有第三代 |
| 记忆会塑造行为 | 语义记忆持续写入、日志里能看到 | 只写不用，未进入 `scoreFn` |
| 人均库存充裕（零死亡） | 存活率 1.00 | 库存被人为容量天花板压在 1.9，触发「余粮不足」闸门 |
| 观察者能看到社交内容 | 发帖事件正常写入 | payload 无 `content`，编年志读不到居民说了什么 |

共同点：**它们在单元层面都是「绿」的**。这五条都是靠端到端跑主循环 + 直接打印运行时状态
才暴露出来的。

## 八、一句话总结

才暴露出来。修复后 437 项测试全绿，两棵树校验 0 error，真实模型 E2E 在环且状态敏感，
