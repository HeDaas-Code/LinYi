## 1. 现状分析

### 1.1 当前 WebUI 架构

当前 WebUI 由 5 个文件构成（~1540 行）：

| 文件 | 行数 | 职责 |
|------|------|------|
| `web/app.py` | 261 | FastAPI 路由 + REST API + 生命周期 |
| `web/templates/index.html` | 188 | 单页 HTML 骨架 + 8 个 view section |
| `web/static/dashboard.js` | 559 | 全部前端逻辑 + Chart.js 图表 |
| `web/static/dashboard.css` | 451 | 暗色主题样式 |
| `web/websocket.py` | 84 | WebSocket 推送 |
| `web/state_provider.py` | 108 | 线程安全状态快照 |
| `web/bus_spy.py` | 73 | monkey-patch 总线监听 |

### 1.2 当前 8 个视图

| 视图 | 数据源 | 交互能力 | 问题 |
|------|--------|----------|------|
| 总览 | `/api/snapshot` | 无 | KPI 卡片 + 2 个柱状图，信息密度低 |
| 脑中世界 | `/sandbox/world` `/sandbox/versions` `/sandbox/characters` | 4 个控制按钮 | 版本树是平铺 badge，不是树形结构 |
| 记忆图谱 | `/memory/graph` | 无 | Canvas 2D 力导向图，节点圆形排列，无交互 |
| TRPG 角色 | `/sandbox/characters` | 无 | 角色卡 + 属性雷达，与脑中世界页重复 |
| 小说手稿 | `/novel/manuscript` | 无 | 纯文本段落展示，无编辑/标注 |
| 总线事件 | `/bus/events` | 筛选 + 清空 | 基本事件流，无 topic 订阅过滤 |
| EOS 指标 | `/eos/metrics` | 无 | 显示 JSON dump，图表数据近乎空 |
| 配置 | `/config` | 编辑 JSON + 保存 | contenteditable pre 标签，无 schema 校验 |

### 1.3 核心问题

**P0 — 架构层面**：

1. **无人格视图**: LinYiProfile（§6.10）是整个系统的灵魂，但 WebUI 完全没有展示人格内核——价值观、特质向量、自我叙事、当前小说项目。用户看不到"林逸是谁"。
2. **无时间视图**: RealTimeClock + DailyScheduler（§9）驱动整个系统节律，但 WebUI 没有时钟/相位/日程甘特图。用户不知道"林逸现在在做什么"。
3. **无社交视图**: SocialInput（§6.3/§16）维护空间、角色、关系、凝视压力，但 WebUI 完全没有可视化。用户看不到"林逸的社会生活"。
4. **无 DMN 视图**: DMN（§6.5）的梦境、反思、心理漫步是核心创意来源，但 WebUI 没有展示。用户看不到"林逸在想什么"。
5. **EOS 是空壳**: Design.md §19 定义了完整的 EOS 体系（Metric / Collector / ObservabilityBus / Dashboard），但当前 WebUI 的 EOS 页只显示 JSON dump，没有真正的指标图表、告警规则、报告导出。

**P1 — 交互层面**：

6. **无外部信息输入入口**: 林逸是常驻自主运行的人格主体，所有经验由 PersonalInput/SocialInput 模块自动生成。外部输入入口（对话/干预）后续单独规划。
7. **控制能力弱**: 只有 4 个沙盒按钮，无法控制 LLM 切换、相位跳转、模块暂停/恢复、记忆巩固触发等。
8. **配置编辑原始**: contenteditable pre + 手动 JSON，没有表单、没有 schema、没有校验、没有分层（§21 定义了 7 层配置）。

**P2 — 技术层面**：

9. **轮询 + WebSocket 双重数据**: `setInterval(loadAllData, 3000)` 每 3 秒拉 9 个 API，同时 WebSocket 也推送 snapshot，数据冲突且浪费带宽。
10. **单体 JS**: 559 行 dashboard.js 包含所有视图逻辑，无模块化，难以扩展。
11. **BusSpy monkey-patch**: 已在审计 issue #6 中指出，不健壮。
12. **无移动端适配**: CSS 有 media query 但只是隐藏侧边栏文字，不是真正的响应式。

## 2. 参考项目 WebUI 特点分析

Design.md §22 明确了五个参考项目。以下分析每个项目的 WebUI 亮点，以及它解决的设计问题。

### 2.1 SillyTavern — 角色卡与提示词组装

**WebUI 特点**：
- **角色卡编辑器**: 结构化表单编辑角色（外貌/性格/背景/示例对话），实时预览最终 prompt
- **World Info Book**: 关键词触发的世界设定条目，带优先级和递归触发可视化
- **Prompt Manager**: 可拖拽排序的 prompt 段落组装器，显示 token 计数
- **聊天界面**: 多角色群聊、正则替换、分支对话树
- **扩展面板**: TTS/STT、图像生成、向量库检索的即插即用面板

**解决的设计问题**: 人格不是提示词中的几行文字，而是可被多模块订阅、版本化、动态演化的配置（§22.1.1 原则）。

### 2.2 MaiBot — 拟人化节奏与记忆架构

**WebUI 特点**：
- **打字动画面板**: 实时展示拟人化后处理（错别字、打字节奏、表情学习）
- **A-Memorix 三维记忆**: 向量记忆 / 图谱记忆 / 时序记忆三个标签页，各自有可视化
- **Planner-Replyer 分离视图**: 显示"先想后说"的两阶段过程，Planner 输出可展开
- **行为学习统计**: 黑话学习进度、表情使用频率热力图
- **状态仪表盘**: 8 维状态（能量/心情/好感/欲望等）的实时雷达图

**解决的设计问题**: 把"像人"拆成认知节奏、表达习惯和记忆更新三个独立维度（§22.1.2 原则）。

### 2.3 astrbot_plugin_private_companion — 状态驱动陪伴

**WebUI 特点**：
- **8 维状态面板**: 能量/心情/好感度/欲望/信任/亲密度/疲劳/兴趣的实时曲线
- **关系状态机图**: 可视化关系阶段转换（陌生人→熟人→朋友→密友），带触发条件
- **状态→行为映射表**: 显示当前状态如何激活不同行为（候选池→闸门→模型判定）
- **主动行为日志**: 记录 agent 主动发起的行为及其触发原因

**解决的设计问题**: 状态不是装饰，而是行为的激活条件（§22.1.3 原则）。

### 2.4 ai-town — 社会模拟与记忆流

**WebUI 特点**：
- **小镇地图**: 2D 俯视地图显示 agent 位置、移动路径、空间中的遭遇
- **Memory Stream 时间线**: 垂直时间线展示观察→记忆→反思→计划的全流程
- **反思日志**: DMN 反思的输入、过程、输出，可展开查看推理链
- **计划查看器**: 每日计划列表，显示完成度、调整历史
- **社交网络图**: agent 间关系强度网络图，边粗细 = 关系深度

**解决的设计问题**: 社会行为不需要硬编码社交脚本，只需要记忆、反思、计划三个机制在共享空间中持续运行（§22.1.4 原则）。

### 2.5 目标驱动持续任务框架 — 四层抽象

**WebUI 特点**：
- **目标层次树**: 长期目标→阶段目标→每日子目标的树形展开
- **决策-执行循环图**: 决策→执行→反馈的环形流程图，高亮当前阶段
- **反馈层仪表盘**: KPI 卡片 + 趋势图，显示目标达成率
- **任务看板**: Kanban 风格的任务卡片（待办/进行中/已完成/阻塞）

**解决的设计问题**: 任何长期自主系统都需要显式的目标层、可评估的反馈层，以及连接两者的决策-执行循环（§22.1.5 原则）。

### 3.2 关键差距总结

当前 WebUI 覆盖了 Design.md 设计空间的约 **20%**：

- ✅ 已有: 沙盒基础控制、小说手稿展示、总线事件流、配置 JSON 编辑
- ❌ 缺失: 人格视图、时间/日程、社交、DMN 梦境/反思、EOS 指标体系、记忆时间线、目标树、状态→行为映射可视化

## 4. 重构方案

### 4.1 设计原则

1. **观测非侵入化** (§22.4 原则 11): WebUI 只读总线，不直接操作模块内部状态（控制操作走 control bus）
2. **人格为中心**: 林逸的人格内核是所有视图的锚点，每个页面都应回答"林逸现在怎么样"
3. **时间为主线**: 所有数据都以时间轴为参照——现在是什么相位、这个相位发生了什么
4. **分层只读 vs 可控**: 观测面板只读，控制面板明确标注为"干预"
5. **移动优先**: 响应式布局，手机也能查看林逸状态

### 4.2 新视图架构

从 8 个扁平视图重构为 **4 大区域 11 个视图**：

```
┌─────────────────────────────────────────────────────────┐
│  导航栏 (左)          │  顶部状态条                          │
│                       │  [相位指示器] [时钟] [能量条] [⚠告警] │
├───────────────────────┼─────────────────────────────────────┤
│  ◈ 林逸               │                                     │
│    ├ 人格画像          │                                     │
│    └ 日记·反思         │                                     │
│                       │                                     │

│    ├ 日程节律          │                                     │

#### 4.3.7 社会空间 (Social Space) — 彻底仿造 ai-town

**来源**: ai-town 像素地图 + 角色精灵 + 对话系统（完整移植）
**对应模块**: SocialInput (§6.3/§16) + SocialSpace / SocialNPC / Relationship / SocialEncounter
**参考源码**: `a16z-infra/ai-town` 的 `PixiGame.tsx` / `Player.tsx` / `Character.tsx` / `PlayerDetails.tsx` / `Messages.tsx` / `conversation.ts` / `movement.ts` / `memory.ts`

### 4.3.7.1 设计理念

ai-town 的核心洞察是：**社会行为不需要硬编码社交脚本，只需要空间 + 移动 + 记忆 + 反思四个机制在共享地图上持续运行**。LinYi 的 Design.md §22.1.4 明确吸收了这一原则。

但 ai-town 是多 agent 小镇（所有角色都是 AI），而 LinYi 是**单主体**（只有林逸是 AI，NPC 是社会环境）。这意味着：
- 林逸是唯一的可移动角色（player），NPC 由 SocialInput 模块的概率引擎驱动出现/消失
- 对话是单向的——林逸"观察"和"参与"社交事件，而非 ai-town 的双向 AI 对话
- 地图不是游戏空间，而是**叙事空间**——林逸在空间中的移动轨迹本身就是一条经验碎片

### 4.3.7.5 记忆与反思 (Memory & Reflection)

**仿造 ai-town 的 `agent/memory.ts` + `reflectOnMemories` 机制。**

ai-town 在对话结束后：
1. LLM 生成对话摘要（第一人称）
2. LLM 评估重要性 (0-9)
3. 生成 embedding 向量
4. 存入 memories 表
5. 当近期记忆重要性总和 > 500 时触发反思
6. 反思生成 3 条高层洞察

LinYi 已有对应机制（DMN 梦境/反思 + MemorySystem 痕迹巩固），但 WebUI 需要可视化这个流程：

```
社交事件 → 碎片提取 → 记忆巩固 → 反思触发 → 灵感产出

在地图视图底部显示遭遇时间线:

┌──────────────────────────────────────────────────┐
│  今日遭遇 (3)                                     │
│                                                    │

### 4.3.7.10 技术选型调整

ai-town 使用 React + pixi-react + pixi-viewport + pixi.js。LinYi 的社会视图如果"彻底仿造"，有两个选择：

**方案 A: React + PixiJS（与 ai-town 完全一致）**

将社会视图作为独立的 React 子应用嵌入 Vue 主应用：

```
Vue 主应用 (仪表盘/人格/记忆/...)
  └── 社会视图 = React 子应用 (PixiGame)
        ├── pixi.js (渲染引擎)
        ├── pixi-viewport (视口控制)
        └── pixi-react (React 绑定)
```

- 优点: 可以直接复用 ai-town 的 `PixiGame.tsx` / `Player.tsx` / `Character.tsx` 代码
- 缺点: 引入 React + Vue 双框架，构建复杂度增加

**方案 B: Vue 3 + PixiJS（原生 Vue 绑定）**

用 `pixi.js` 原生 API + Vue 3 组合式函数封装：

```typescript
// composables/usePixiMap.ts
import * as PIXI from 'pixi.js'
import { Viewport } from 'pixi-viewport'

export function usePixiMap(container: Ref<HTMLElement>) {
  const app = new PIXI.Application({ ... })
  const viewport = new Viewport({ ... })
  
  onMounted(() => {
    container.value.appendChild(app.view)
    app.stage.addChild(viewport)
  })
  
  onUnmounted(() => app.destroy())
  
  return { app, viewport }
}
```

- 优点: 统一框架，构建简单
- 缺点: 需要手动实现 ai-town 已有的 pixi-react 绑定

**推荐: 方案 B** — LinYi 的社会视图与 ai-town 有本质差异（单主体 vs 多 agent），直接复用 ai-town 组件的价值不大。用 Vue 3 + pixi.js 原生 API 更干净，且 pixi-react 只是一层薄封装，手动实现成本不高。

### 5.1 前端技术选型

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **A: 原生 JS + D3.js** | 零构建、无依赖、与现有代码兼容 | 大型应用难维护 | ⭐⭐ |
| **B: Vue 3 + Vite + D3.js + PixiJS** | 渐进式、SFC、PixiJS 做像素地图 | 需构建步骤 | ⭐⭐⭐⭐ |

**推荐: 方案 B — Vue 3 + Vite + D3.js + PixiJS**

1. LinYi 是常驻运行的 agent，WebUI 会持续增长，需要组件化

3. D3.js 处理记忆图谱、版本树、社交网络图等 SVG 可视化
4. **PixiJS 处理社会空间视图的像素地图 + 角色精灵**（仿造 ai-town 的渲染管线）
5. pixi-viewport 提供地图拖拽/缩放/滚轮交互
6. Chart.js 保留用于简单图表（KPI 趋势线等）
7. Vite 构建快，热更新好

### 5.4 数据流架构

当前问题: `setInterval(loadAllData, 3000)` 每 3 秒拉 9 个 API + WebSocket 推送 snapshot = 数据冲突。

重构方案:

```
┌─────────────┐     WebSocket (主)      ┌──────────────┐
│             │ ◄───────────────────── │              │
│  Vue Store  │   增量更新 (diff patch)  │  FastAPI     │
│  (Pinia)    │                        │  后端         │
│             │ ◄──── REST (按需) ──── │              │
└──────┬──────┘   历史数据 / 搜索       └──────┬───────┘
       │                                        │
       │  ┌─────────────────────────┐          │
       │  │  useAgentSnapshot()      │          │
       │  │  - WS 推送 → 增量 patch  │          │
       │  │  - 视图切换 → REST 拉取  │          │
       │  └─────────────────────────┘          │
       │                                        │
       │  ┌─────────────────────────┐          │
       │  │  useBusEvents()          │          │
       │  │  - WS /ws/bus 实时推送   │          │
       │  │  - 本地缓冲 + 过滤       │          │
       │  └─────────────────────────┘          │
       │                                        │
       │  ┌─────────────────────────┐          │
       │  │  useClock()              │          │
       │  │  - WS 推送 phase.changed │          │
       │  │  - 本地时钟同步          │          │
       │  └─────────────────────────┘          │
```

**关键原则**:
1. **WebSocket 推送增量**: 不再推送完整 snapshot，只推送变化的字段
2. **REST 按需拉取**: 视图切换时才拉取该视图的详细数据
3. **本地状态合并**: Pinia store 合并 WS 增量和 REST 全量
4. **事件流独立通道**: 总线事件走独立的 `/ws/bus` WebSocket，避免与 snapshot 混在一起

### 5.5 顶部状态条 (全局组件)

参考 astrbot 的 8 维状态面板，在所有页面的顶部显示林逸的当前状态:

```
┌──────────────────────────────────────────────────────────────┐
│  [☾ 下午推演 16:08]  [能量 ▓▓▓▓░ 78%]  [情绪 😐 0.5]  [⚠ 1]│
└──────────────────────────────────────────────────────────────┘
```

- **相位指示器**: 当前阶段名 + 图标 + 模拟时间
- **能量条**: 代谢层 energy 值，低于 20% 变红
- **情绪**: 当前情绪状态（从 Metabolism 或 SocialInput 获取）
- **告警计数**: EOS 活跃告警数，点击跳转到 EOS 页

## 8. 关键设计决策

### 8.1 为什么不直接用 SillyTavern 的 UI？

SillyTavern 是**对话驱动**的，核心是 chat。但 LinYi 是**自主运行**的，核心是"大脑内部发生了什么"。LinYi 的 WebUI 不是聊天界面，而是**脑内观测台**。

### 8.2 为什么不用 Grafana 做 EOS 仪表盘？

Design.md §19.3.4 明确定义了 Dashboard 是 EOS 模块的一部分，通过总线订阅数据。如果用 Grafana，需要额外的数据导出管道，且无法与总线事件实时联动。自建 Vue 组件可以深度绑定总线数据流。

### 8.3 为什么选择 Vue 而非 React？

1. LinYi 团队是 Python 后端为主，Vue 的模板语法更接近 HTML，学习成本低
2. Vue 的 Pinia 状态管理足够用，不需要 Redux 的复杂度
3. 单文件组件 (SFC) 天然按视图拆分，与 11 视图架构匹配

### 8.4 外部输入入口

对话/外部信息输入入口暂不纳入本次重构范围，后续单独规划。当前 LinYi 是纯自主运行：所有经验由 PersonalInput/SocialInput 模块按代谢/时钟驱动自动生成，WebUI 是观察台而非操作台。

## 9. 风险与注意事项

1. **后端 API 扩展量大**: 从 9 个端点扩展到 40+，需要确保每个端点都有线程安全保护（参见审计 issue #2）
2. **前端构建依赖**: Vite + Vue + PixiJS 需要 Node.js 构建链，但当前项目是纯 Python。建议在 `pyproject.toml` 中添加可选的 `[webui]` 依赖组
3. **WebSocket 连接管理**: 从 1 个 WS 扩展到 3 个 (snapshot + bus + social)，需要确保 ConnectionManager 能处理多连接
4. **LinYiProfile 演化历史**: 当前 IdentityCore 不记录特质变化历史，需要新增 `_trait_history` 字段
5. **DailyScheduler API**: 当前没有暴露 `DailyPlan` 的 REST 端点，需要新增
6. **EOS 指标实现**: Design.md §19 定义了完整的 Metric/Collector 体系，但当前 EOS 模块实现程度未知，WebUI 的 EOS 页面取决于后端指标是否真正实现
7. **Tiled 地图制作工作量**: 5 张像素地图需要用 Tiled Map Editor 手工制作，每张约 2-4 小时。可考虑用程序化生成替代（如房间生成器）
8. **角色精灵资产**: 林逸 + 10 个 NPC 各需一套 4 方向×4帧行走动画。可先用 ai-town 的 MIT 精灵图占位，后续定制
9. **PixiJS 性能**: 像素地图 + 多角色精灵在移动端可能卡顿。建议限制 NPC 同时显示数量（每空间 ≤ 5 个），精灵帧率 12fps
10. **SocialInput 后端适配**: 当前 SocialInput 模块不暴露 NPC 实时位置和遭遇对话内容，需要扩展 `to_dict()` 和新增 API 端点
11. **单主体 vs 多 agent 差异**: ai-town 的对话是两个 AI 实时交互，LinYi 的社交事件是 SocialInput 引擎预生成。WebUI 显示的是"回放"而非"实时对话"，这降低了 WebSocket 的实时性要求但增加了历史数据查询需求
